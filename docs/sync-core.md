# Synchronization core

`buildPlan` is a deterministic calculation over a feed, Notion snapshots, configuration, and a supplied time. It performs no I/O and does not mutate its inputs.

## Planning

- `course-catalog.ts` collects course matches and blank-field enrichments in a run-local catalog. Provisional identities remain stable and are never deleted or reused. After collection, source labels/IDs associated with existing courses resolve provisional members. Multiple destinations stay ambiguous; incompatible metadata blocks the affected work. Redirects recheck earlier metadata against the final destination.
- `assignment-decision.ts` computes the permitted property patch and description audit decision for one assignment. Blocked course work can still receive an exact-UID lifecycle update. Due-date override rules live in `date-resolution.ts`.
- `plan.ts` emits assignment decisions only after course resolution finishes. It returns planning facts (conflicts and avoided/deferred audits) from those final decisions, rechecks duplicate evidence when a course destination changes, and then calls the removal-evidence policy with the full protection set. Duplicate Notion UIDs are protected even when absent from the feed. Missing evidence on any page whose UID the feed shows, including a quarantined UID with no assignment update, is cleared before absences are evaluated.
- `feed-diagnostics.ts` keeps feed diagnostics separate from assignment work. Ordinary calendar events, quarantined source data, and reconciliation skips retain their distinct meanings.

Because decisions are emitted only after course resolution, a later course conflict never redirects a queued assignment patch, undoes a description metric, or prunes an already counted unchanged assignment.

## Execution and recovery

`commands.ts` compiles the plan into one ordered sequence: course writes, active assignment writes, explicit cancellations, missing evidence, and inferred removals. Both `applyPlan` and the report's operation sections use that sequence, so failure accounting cannot drift from the actual write order.

`reconcile.ts` executes assignments sequentially. For an update requiring description verification, it verifies/repairs the body first, then commits independent properties and verified metadata together. If description work fails, it still attempts the independent properties. If the combined commit fails, it attempts only the independent properties separately, retains the metadata failure (including ambiguity), and stops before later assignments or removals. The ledger records confirmed logical effects, every failed substep, unattempted commands, and assignments requiring repair; property fallbacks mean applied effects need not be a plan prefix. Counts match effects by operation kind and target. Create recovery and confirmed-create counters remain separate; an assignment update is counted only after all its commands succeed.

The Notion adapters are responsible for unique-page recovery, template stabilization, managed-section verification, and ownership-safe property serialization. Description metadata is committed only after body verification. A block append with no visible progress stops as ambiguous rather than appending again; a later run can resume the visible pending replacement. SDK retries are disabled so the gateway's bounded retry policy and physical request metrics are authoritative.

Managed sections create a pending marker with its first batch of children. Acknowledged appends advance a cursor; one complete child read verifies the final body before marker promotion and old-section deletion. Ambiguous or incomplete responses trigger immediate observation and may resume only from a verified, advancing prefix. Batches respect both the 100-child limit and a conservative UTF-8 byte budget. Successful multi-batch writes therefore require linear paginated reads rather than re-reading every accumulated prefix.

Assignment creation reuses the root blocks from the final template observation. Because [Notion applies templates asynchronously](https://developers.notion.com/guides/data-apis/creating-pages-from-templates), stabilization requires two equal, nonempty recursive observations at a default one-second polling interval. Reusing the final observation adds no assumption about template timing or readiness.

## Reporting and request metrics

- `observability/run-report.ts` derives reporting from the plan, execution ledger, feed diagnostics, and a request snapshot. `buildPlan` takes no mutable metrics/counters; `applyPlan` takes no counts. Adapters return create/description outcomes; managed-section recovery explicitly notifies the execution ledger, including recoveries before a later failure.
- `plannedCounts` describes intended work; `executedCounts` describes confirmed outcomes. Feed diagnostics, unchanged/skipped decisions, and newly observed missing candidates are planning context in both. `counts` selects planned counts in dry runs and executed counts otherwise. A dry run performs reads but has zero executed writes/audits.
- `Created` means confirmed assignment page creations, excluding recovered creates. Added pages include both. A created page can still require repair; an assignment update counts only when all its substeps finish. Missing-evidence changes count as soon as their property command succeeds, even if description work fails. Failed/ambiguous operations never count as applied; the ledger retains all unattempted commands.
- Description audits due/deferred/avoided come from planning. Audits run/body reads count attempted logical audits (including a failed read), not HTTP calls or template polling. Passed/repair/replacement metrics require a successful body outcome, even if the subsequent metadata commit fails. `failedOperation.outcome` is the authoritative record of whether a failed write was ambiguous.
- The required gateway `requestMetrics` contains only physical Notion attempts, operation breakdowns, read/property retries, and throttle retries with their total wait. A throttle retry follows a `429` or `529` on any operation and waits the `Retry-After` delay, capped at 60 seconds, or the backoff delay when there is no header; a throttled read or property update counts in both its own retry metric and the throttle metric. Pagination, recovery polling, and failed requests all count; SDK retries are disabled. Each run subtracts a copied starting baseline, so reusing a gateway cannot contaminate results. Concurrent reads settle before failure finalization.
- Both outputs use a snapshot taken before Sync Log persistence. Requests for report persistence are returned separately as `reportingRequests`; adding these to `metrics` gives the full run's requests. A new Sync Log includes its complete managed body in the create request when it fits the batch limits; the acknowledged create completes persistence. Reused or ambiguously-created pages use observed managed-section reconciliation. Oversized bodies also use the batched protocol. A Sync Log failure changes the returned status/errors without rewriting completed sync work or retrying log creation. A stored log cannot describe its own subsequent persistence failure.
- `observability/report-content.ts` centrally defines aggregate report fields and operation sections. The GitHub Actions summary uses only aggregate status, counts, metrics, warning codes, and a non-identifying failure summary; detailed operation sections appear only in the Notion Sync Log. The report needs no Sync Log properties beyond those in the [setup checklist](notion-setup.md).
- Operation lists over 20 entries show exact totals by kind and the first/last five examples with an explicit omitted count. Failure, partial-execution, warning, and error details are never abbreviated. Sync Log lines are packed into bounded paragraphs without truncation; the full execution ledger remains in the run result. Description rich text and Sync Log paragraphs share one text splitter that prefers whitespace and never splits a surrogate pair, so emoji at a chunk boundary cannot produce a lone surrogate that Notion rejects. Descriptions themselves are parsed from turndown's Markdown into a flat document model (`description-document.ts`) that both the Notion block renderer (`notion/description-blocks.ts`) and the `Raw Description` excerpt derive from; the managed-section canonical form covers list items, quotes, and code blocks so read-back verification treats styling and links as content. How a run is segmented into rich-text items is not content: Notion may merge or re-split adjacent items, so the canonical form joins neighbouring text items that share a link and annotations before comparing. A replacement that still cannot be verified fails with the first differing block, path, and a short excerpt of each side.

## Validation

The fixture, reconciliation, application, description audit, health-monitor, and observability suites cover end-to-end behavior. `sync-core.test.ts` covers course-order, ambiguity, metadata, duplicate protection, repeated-run convergence, snapshot preservation, and execution-ledger regressions. `recovery-boundaries.test.ts` checks the real SDK retry boundary with mocked HTTP and managed-body recovery after delayed visibility. Application tests can inject a clock so removal-window assertions do not expire with calendar time.

`notion-write-path.test.ts` checks physical SDK request budgets, pagination, large logs, batched ambiguity, independent property fallbacks, and template snapshot reuse. With a stable one-block template and short description, assignment creation uses 8 requests; an unchanged description audit plus property update uses 3; a new compact Sync Log uses 2. A new 1,000-block managed section uses 12 reads and 11 writes, with no retries or ambiguity.
